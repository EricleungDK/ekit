# mech-review-mutants/stacks/misuse: misuse, a result with no or a malformed stack field is named and never counted; a stack given twice is one CI entry

- story: As a repo owner whose report job is mis-wired (a result written without the stack field, a hand-edited or truncated one, a result of the right stack from another folder, a whole leg of another stack, a stack listed twice in `stacks.json`), I get one named CI `fail` entry per problem, nothing from the bad result counted, and a failing check; never a silent pass.
- covers: #62 62.3 (no `stack` field, `null`, a string, a list, `{}`, an empty stack or folder, no folder, a folder that is a number: each one CI `fail` entry `result has no stack field` / `result has a malformed stack field`, the result's MISSED mutant not counted, with and without `--project-dir`; every shard bare: one entry per shard, nothing counted); 62.1 (a duplicated stack, by name or by stack and folder under another name, twice or three times, also when the first row has no result: exactly one CI `fail` entry naming it; other stacks still report; another folder of the right stack is named with its folder, and counted when `--project-dir` is unset; a whole leg of another stack: one entry per result); 62.5 (a wrong-stack and a no-stack-field entry reach the sticky comment in the leg's rows and fail the check)
- steps:
  1. Parent's install and repo; api's shard 1 with a survivor (`return n + 2 -> return n - 2`), web's shards clean.
  2. Copies of api's shard 1 with each bad `stack` field, merged as shard 1 of `merge --stack python [--project-dir api] --shards 2`; then both shards without the field.
  3. api's shard 1 with `stack: {python, lib}`, with and without `--project-dir`; web's two shards as api's.
  4. Fake GitHub, `mech-comment.py --stacks`: web alone; rows api, web, api; api, web, api2 (python in api); api three times; an api row whose r2 file was never written first, then api; api's merge holding the wrong-stack entry, then the no-stack-field one.
- expected: step 2 every merge exit 1, R3 fail, exactly one CI entry `mutants shard 1/2 produced no result: <why>`, no R3 entry, tested 1/1; all bare: two entries, no R3 entry. Step 3 `result is for stack python in lib, not python in api`; unset `--project-dir`: the MISSED counted; web's shards: one entry per shard. Step 4: web alone exit 0; each duplicate exit 1 with exactly one CI `fail` entry (`stack api (python in api) given twice ... the second is not counted`, `again as stack api2 (python in api)`, `given 3 times ... only the first is counted`), api's MISSED shown once, web row pass; a first row with no result also has its `produced no result` entry; the merge's entries in stack `api`, api row fail, exit 1. No traceback; the caller checkout untouched.
