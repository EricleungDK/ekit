# stack-plan: the drift check holds the repo's manifests to `.ekit/stack-plan.toml`, judged by the base branch's plan

- story: As a repo owner with several projects I commit a stack plan, and on every PR the drift check (`mech-review.py drift`, as the guard job runs it) blocks a manifest no stack covers, tells me when a planned stack's checks start, a retiring stack is still there or a stack's manifest is gone, and cannot be talked round by a plan entry added in the same PR; a repo with no plan sees nothing new.
- covers: #56 56.2 (an uncovered manifest blocks, outside fixture/vendor/build folders and the ignore list; planned stack's manifest appears with a proven adapter → "its checks start"; retiring stack's manifest still present → message; a stack's manifest gone → message naming the entry to remove); 56.3 (two uncovered manifests → exactly one `fail` entry of class `adapter-fix` naming both); 56.4 (base plan judges; a PR changing only the plan or an adapter file and adding no manifest is judged by its own plan: the setup PR passes; a PR adding a manifest and its entry together stays blocked); 56.5 (no plan → no D, resolve as before)
- steps:
  1. Clone the kit from `$EKIT_REPO` (the install); every call is `python3 -I <clone>/scripts/mech-review.py drift --repo R --base B --head H` (JSON, and `--format text`).
  2. No plan on base or head, a PR adding `api/pyproject.toml`: exit 0, checks R1-R4 only, no entry, no `D` in the summary; `resolve` gives `ts`, `web`, no error, `linux`.
  3. Base plan: `ignore = ["samples"]`, `app` (rust, current), `legacy` (ts, retiring), `svc` (python, planned), `mob` (planned, adapter file `.ekit/adapters/kt.toml` not written yet). base..base: exit 0, D pass, one message (retiring legacy).
  4. PR adds `svc/pyproject.toml`, deletes `app/Cargo.toml`, adds `package.json` under samples, tests, node_modules, vendor, build, dist, fixtures, testdata, examples, third_party, target, and `mob/build.gradle.kts`: exit 0, no entry, three messages (svc's checks start, remove the entry `app`, legacy still there), none for mob; text format the same with three `message:` lines.
  5. PR adds `tools/gen/package.json`: exit 1, one entry `D adapter-fix fail .ekit/stack-plan.toml` naming it.
  6. PR adds `api/pyproject.toml` and `cli/Cargo.toml`: exit 1, exactly one fail entry, class adapter-fix, naming both; one `fail D-` line in text.
  7. Which plan judges: a setup PR (base has manifests and no plan; the PR adds the plan and an adapter file only) exit 0; a PR adding `cli/Cargo.toml` with its entry exit 1 naming only `cli/Cargo.toml` (also with no plan on base); the entry first (plan-only PR, exit 0), then the manifest (exit 0, its checks start); a PR that only fixes an adapter file's `manifests` exit 0; the same fix with a new manifest exit 1.
- expected: exit codes, entries and messages as above; no traceback; nothing written into the kit repo.
