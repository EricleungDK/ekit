# mech-review-baseline/python-cost: a python baseline measures the suite's test time once and sizes the shards from it: one for a small PR, at most 4 for a costly one, never more than the mutants; merge accepts them

- story: As a Python repo owner I let the `baseline` step pick the shard count: it runs my suite once, puts the measured test time in its JSON, and asks for one shard on a cheap PR and up to 4 on a costly one, never more shards than mutants; the shards it asks for run every mutant once and `merge` accepts them.
- covers: #64 64.1 (count = min(4, mutants, ceil(estimate / (budget / 2))): 8 mutants x 0.5 s -> 1; x 60 s -> 2; x 90 s -> 3; x 120 s -> 4; x 600 s -> 4 with and without `--shards 4`; budget 60 -> 1; `--max-mutants 2` -> 2, 1 -> 1; 3 mutants at 80 min -> 3; no mutant on a changed line -> 0 shards, R3 pass); 64.2 (the baseline runs the suite once with `--junit-xml`; `checks.R3.timing.baseline_test_s` holds the session time the XML gives; the note names the estimate; `timeout` null); 64.4 (merge accepts the measured baseline's 4 shards: 8/8, no CI or env entry, the baseline time once, each mutant in one shard; a survivor is one MISSED entry; with `--max-mutants 5` on baseline and shards, 2 shards and `partial: R3 (5/8)`)
