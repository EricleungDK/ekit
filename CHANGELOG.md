# Changelog

Releases are tags `vX.Y.Z` that match `version` in `.claude-plugin/plugin.json`; each one moves the floating `v0` tag that CI callers follow.

## Unreleased

### Added

- **Default verify commands at session start** (#61): the SessionStart hook resolves the stacks at HEAD as CI does (`stack_plan.stacks_at`: the plan's stacks to run, else `stack: auto` detection with the repo's adapter files) and declares each one's verify commands for the session, in task-verify's store, so `task-verify.py run` and the Stop gate match the same string: `build` and `lint` from an adapter file's `[commands]`, `test` as R1 and R4 run it (`test_cmd_in`: an adapter file's `[run]` runners or a built-in's; `[commands].test` for a file with no `[run]`), never `install`. A stack in a folder runs as `cd <folder> && <cmd>` (a POSIX shell line; a folder led by `-` as `./-x`); a folder or command holding a run of whitespace, which task-verify collapses, is not declared and is named. The context lists what the store holds after declaring, each command with every stack and step it serves. The context names each command with its `run` line, and once per stack each step it names no command for. Several projects or none, a plan or adapter file that does not read, python < 3.11, no session id, a resolution past the hook's 3 s and any other error declare nothing, in one line that says why. The agent may still declare extra commands per task; the defaults stay alongside them.
- **CI passes the issues a PR closes to R2** (#53): the workflow's R2 guard reads the closing keywords of the PR body (`Closes #N`, `fixes owner/name#N`, an issue URL; this repo only) and passes each as `--linked-issue N`, so a `spec: #N reverses <test>` line turns that removal into a `confirm` in CI. No new permission: callers keep `contents: read` and `pull-requests: write`.
- **A test the spec reverses is a `confirm`, not an owner waiver** (#53): `r2` and `all` take `--linked-issue N` (repeatable; CI passes the PR's closing issues). A removed test that a line of a commit message `spec: #N reverses <test name>` names, N linked and the name exact, is one R2 `confirm` ("test `<name>` removed, spec #N reverses it"), which the reviewer confirms only against a quoted sentence of #N, else the test is restored. It covers a one-line test, which #41's rename match cannot. Several linked lines for one test use the lowest N. No line, an unlinked issue, another name, or one name removed from several files keeps the `fail`. Nothing is waived.
- **One R3 run per env dir** (spec #78's retro): `scripts/r3-local.py` locks its `--env-dir` for the run (`flock` on `.ekit-r3-env.lock`, holding the run's pid). A second run on the same dir exits 2 before any step, naming the first run's pid, instead of replacing its venv, head checkout and shard results. The lock goes with its process, so a run killed by a restart leaves none behind.

The format and engine gain what Java needed: **declared tests** (`[tests] style = "declared"`, `prefix`: a test is a `[functions]` shape with a case marker before it, `@Test void adds()`, grouped by `class NAME {...}`, a skip marker on the method or class), **`{module}`** in `[mutation.tool].mutate` (a changed file under one of `module_roots` as its dotted name, PIT's class name; a changed file under none is `n/a (env)`), and **`test-paths`** in R0's runtime `controls.json` (a fixture project whose tests sit outside `tests/`, Maven's `src/test/`). Review round 1: `{package}` beside `{module}` (the reference mutates `{package}*`: a second top-level class in a changed file too); a changed file under no `module_roots` is left out of the run and named in the note, never `n/a`; `[mutation] skip_annotations` (declared style: `@DoNotMutate`, `@Generated`, `@CoverageIgnore` are mutation skip markers) and `config_files = ["pom.xml"]` (a pom edit is R2's `needs-human` entry, since the pom configures PIT); PIT is pinned in the adapter (`org.pitest:pitest-maven:1.17.4`), the pom still gives its config and `pitest-junit5-plugin`; JUnit's condition annotations (`@DisabledOnOs`, `@EnabledOnOs`, ...) skip like `@Disabled`; a generic test method is read past its `<T ...>`; `@TestFactory` is no case. **Changed**: an adapter file's `[run.outcome] env` pattern reads only when no count was read, so a failing test that prints the toolchain's message stays `fail`; `all --adapter FILE` proves FILE with its own fixtures (`FILE.r0/`) and bytes, as `r0 --adapter` does, unless a built-in of its name ships fixtures. Review round 2: a marker may have whitespace, line breaks and comments after its prefix and around its dots (`@ Disabled`, `@/**/Disabled`), as javac allows; `[lexer] unicode_escapes` (the reference sets it) decodes `\uXXXX` before reading, as javac does, so `\u0040Disabled` skips; `skip_annotations` match by suffix, as PIT does (`@MyGenerated`); `config_files` takes paths (`.mvn/maven.config`), and the reference names `.mvn/maven.config`, `jvm.config` and `extensions.xml`; `{package}` of a file in the default package is its own class (`Top*`: PIT refuses a bare `*`). **Changed**: a declared mutation tool (an adapter file's `[mutation.tool]`, `ts.toml`'s Stryker too) that ran and wrote no report is an R3 `fail` with one `agent-fixable` entry, no longer `n/a (env)` (a toolchain absence); the built-in ts keeps `n/a (env)` for now; when the output shows a dependency fetch failed (`Could not resolve`, `Could not transfer artifact`, `Unknown host`) the entry is a `CI` one (class `env`), still a fail. A source in which a unicode escape decodes to a line break (`\u000a`, `\u000d`) is unparseable under `unicode_escapes` (R2's `needs-human` fail): it would move every later line off the diff's.

- **Co-change rules: proof cases and guards** (#85): each rule gains two proof cases, `flagged` (the paths of a PR it must flag) and `control` (of one it must leave alone). When a PR changes `.ekit/co-change.toml`, R2 guards it: a head file that does not read is a `fail` entry (no longer unnoticed); a new rule whose incident resolves to no commit the head reaches or `#N` a commit message names, or that lacks a case, is a `fail` entry; a rule that fires in the range and is weakened (lower severity, a trigger glob gone, a require glob added) or removed in it is a `fail` entry of class needs-human. Adding and promoting a rule give none. In `all`, R2's status no longer counts R0's entries. See [CI doc](docs/mech-review-ci.md#co-change-rules).
- **The `mistake-to-check` skill** (#87): takes one agent mistake with its evidence (the failing run, the commit or PR) and either makes the check or gives one `No check:` line saying why none. - **R0, the adapter proof: runtime half** (#21): the adapter measured against the test runner. `red --r0 DIR` (also `all`) runs the run part: the **census** (every test the runner lists is found by the scanner, `found/listed` with the misses named, on the repo at head, at least `[limits] census` percent, and on the fixture project; an empty listing beside scanner tests fails, never `0/0`; a runner with no listing, such as jest, a unittest command or an adapter file without `[run.list]`, reads `n/a` with the reason), **assert density** (the repo's tests with no recognised assert, listed, measured on every run; over `[limits] assert-density`, default 10%, one `needs-human` entry naming them, which blocks no other check, until a person accepts them in `.ekit/r0-accepted.json` at the base: `{"assert-density": {"<stack>": ["path::test"]}}`; a PR that adds a name there is a `needs-human` entry of R0's editing rules) and the **runner controls** (fixture tests read `pass`, `fail`, `none` (skipped), `build` and `none` (no such test), and the skipped one carries the adapter's skip marker). `mutants --r0 DIR` (shard 0) runs the **R3 control**: R3 on a weak-assert fixture PR gives a MISSED mutant, on the strong one none. Version probes keep #19's program rules (on PATH's absolute entries or absolute, never in the checkout, never a launcher an adapter file names, a cargo subcommand's binary too; `--version` in an empty dir with a minimal environment); a refused one is named, not run. The merge combines the guard's static half and both parts into one R0. `r0 --fingerprint run|r3` prints the part's fingerprint and cache key. Runtime fixtures ship for rust, python and ts (`r0_fixtures/<stack>/runtime/`, and `runtime-jest/` for a jest checkout: a fixture dir's `runtime-<runner>/` is used when the checkout picks that runner); the R3 control refuses a tool that resolves into the reviewed checkout, as R3 does; `tests/fixtures/adapters/minirun.toml` is a fixture adapter with every part. The workflow's `red-first` and `mutants` (shard 0) jobs compute the fingerprint, remove `~/.cache/ekit-r0`, restore it with `actions/cache` (pinned) under its key and pass `--r0`; a hit needs the same PR re-running at the same fingerprint (warming from the default branch is a follow-up). JSON the runtime half reads keeps the engine's nesting limit. Format: `docs/mech-review-ci.md#runtime-half`.

- **Parser-backed adapter files** (#27): for a language the lexer table cannot describe, an adapter file may declare `[parser]` (`command`; `installer`, `package` and a pinned `version`; optional `timeout` and `skipped_text`) in place of the pattern tables (`[lexer]`, `[tests]`, `[functions]`, `[asserts]`, `[[suppressions]]`, `mutation.skip_comments`: an error beside it). The command gets one file's text on stdin and its path as its last argument, in an empty temp dir with a minimal environment (no token, no project config) and a timeout, and prints the file's facts as JSON (tests with spans, markers and calls; asserts with operands; suppressions; mutation skips; a parse error), which the core checks strictly against its schema (`scripts/mech_review/parser_cmd.py`; stdlib only). The command is split into argv at load, never run through a shell; a relative program path, unbalanced quotes or an unpinned version are load errors. The command is an allowlist: one bare program name that is no interpreter or shell, then long options only (`--name`, `--name=value` with a plain value); anything else is a load error. The core builds the install steps from `installer` (pip, npm, cargo, gem or go), a validated package name and one exact version into a prefix of its own (`parser_cmd.install_steps`; only the parser package is pinned, its dependencies resolve at install time), and runs the program from that prefix only, never from PATH (`$EKIT_PARSER_HOME`, else `~/.cache/ekit/parsers`); a program the package did not install is the one `CI` entry. A command word holding a path inside the reviewed checkout is refused before it runs, in R2 and R0 alike. ekit does not sandbox the parser: the base adapter's command is owner-trusted config. A command that cannot run, exits non-zero, times out or prints invalid facts gives one blocking `CI` entry (class `adapter-fix`), never `n/a` and never a pattern fallback. R0 proves a parser-backed file as it proves a pattern one, but runs its parser only when the file's `[parser]` equals the base branch's: else every source case is `unproven` and one `needs-human` entry says the parser command changed. A repo's adapter file found by name at the base (#17) takes the same parser path, and R0 proves its base copy. The workflow installs the parser from the base's adapter file (`mech-review.py parser-install`, below). Format: `docs/mech-review-ci.md#parser`.

- **R0, the adapter proof: static half** (`scripts/mech-review.py r0`, #20): the stack adapter must catch every R2 cheat (delete, comment out and rename a test, made by the core from a seed; skip, a changed expected value, a weakened assert, a suppression without a reason, from fixtures) and give no entry on the negative controls (a rename with the same asserts, reordered asserts, asserts moved into a helper, the empty diff of every fixture), each run as a PR in a throwaway repo; an adapter file with a bad `ident_chars`, no assert shape or an unbalanced bracket pair must fail to load cleanly. Loosening a limit (an adapter file's `[limits]`, the caller workflow's `max-mutants` and `mutation-budget` inputs, the plan's `ignore` list) or changing a target OS is one `needs-human` entry, stacks matched by folder; tightening needs no one.   - **`scripts/preflight.py` replaces `preflight.sh`**: the same checks, plus the OS name first, an install line per missing tool for this OS (`brew`, `winget`, `apt`), and a warning when `git config user.email` is not a GitHub noreply address while the remote is GitHub (the address itself is never printed). `--env` names the shell it was run from: `Env: unsandboxed; shell: bash`.
  - **The plugin dir comes from the `CLAUDE_PLUGIN_ROOT` env var**, read by each shell (`"$CLAUDE_PLUGIN_ROOT/…"`, `"$env:CLAUDE_PLUGIN_ROOT/…"`), never from the path Claude Code would paste in place of `${CLAUDE_PLUGIN_ROOT}`: a `'`, `$` or backtick in that path broke every hook. In Git Bash the `/c/...` root goes through `cygpath -m` (MSYS converts no argument holding a `'` for a native Python). Printed paths take one form both shells read alike, whichever printed it: single quotes, or double quotes for a path with a `'` and no `$`, backtick or `"`; a path with a `'` and a `$` or backtick has no such form and is double-quoted (it then names no file: a loud failure).
  - **Windows smoke** (`tests/windows-smoke.py`, not a unittest module): in the real shells of a Windows machine, the hook command in PowerShell, every hook in plain PowerShell with no Git Bash on PATH (plugin dir holding `'`, `$` and a space), verify commands declared in PowerShell and in Git Bash each re-run in its own shell, and a scenario timeout with only Git's `cmd` dir on PATH. `tests/launcher.test.sh` runs the hook command's sh part on every OS; `tests/run.sh` runs the smoke on Windows (MINGW/MSYS). The unit tests fake the shells, the process table and the files on disk, so they run everywhere without a skip.

- **Scenarios as `run.py`, the portable default** (#59): a scenario's run file may be `run.py`, run with the Python running the runner (the one the hooks found), so a scenario needs no bash on any OS; `run.sh` (bash, Git Bash on Windows) and `run.ps1` (`pwsh`, else Windows PowerShell, `-ExecutionPolicy Bypass`; called from `-Command`, since `-File` exits 0 whatever the last native command gave: its exit code is the script's own `exit N`, else 1 when an error stops it, else the last native command's exit code (0 if none ran). That is not bash's last-status rule: a native failure the script handled, then cmdlets, reads FAIL with that code, and a `$LASTEXITCODE = 0` in the script sets only a script-scope copy, so a run.ps1 that handles a native command's failure ends with `exit 0`; its path goes to pwsh as one literal, and to Windows PowerShell 5.1, which globs a command path, with `[ ] * ?` and backticks escaped: the 5.1 form is checked by reading PowerShell's source only, the Windows smoke runs pwsh) still run wherever that shell is. taste-it writes `run.py` unless the user asks for a shell; `drivers.md` shows the install commands as argv lists. A host without the run file's shell reads the scenario `NOT-RUN <id>: bash is not on this machine (env)` (`PowerShell is not ...` for run.ps1), never PASS and never a plain FAIL: results.json's verdict is `NOT-RUN` when nothing else failed, `run` exits 1, `check` says `cannot run here: ...` (for a full run on the files as they are; else `partial run` or `stale`), `can-fail` reads it `N/A` (exit 4), and the Stop gate takes `## Finish: blocked` naming it. A folder with two or more run files is a FAIL naming them all (`more than one run file (run.py, run.sh): keep one`), never a silent pick, and in `can-fail` an `ERROR` line with exit 2. A scenario runs without the caller's `PYTHONOPTIMIZE`, `PYTHONSAFEPATH` and `PYTHONINSPECT`, so a run.py's failed `assert` is a FAIL, a helper beside it imports, and its `sys.exit(N)` is its exit code. For every run file a timeout stops every descendant of the scenario and is a FAIL: on POSIX each one found by parent pid (`ps`), a child in a session of its own (`setsid`, `start_new_session`) and what it started included, then the process group; on Windows the job object, which holds every descendant. A background child goes with its scenario at a normal exit (its process group, or the job); on POSIX a child that started its own session and outlives a normal exit (an orphan) is not tracked. untracked bytecode is no repo change, a failed transcript is kept, and artifacts are listed; the transcript names the real command (`command: python run.py`). preflight reads a `run.py` or other Python helper, in any case (argv lists or tuples, `which(...)`; the name raw or not, in any case), and a `run.ps1` (command position) for the driver tools they start; a one-string command line (`shell=True`), `os.execlp`, a full path, an argv built in a variable and `Start-Process` are not read, and `print("curl")` or `re.search("curl", ...)` reads as a use. `tests/windows-smoke.py` runs run.py scenarios (and a run.ps1) in plain PowerShell with no bash on PATH.

- **taste-it seeds scenarios from what the user asked for** (#60): for a new app, taste-it reads the user's description and the stories saved in the repo (issues, specs, PRDs, notes), proposes one scenario per described feature and shows each one's wording; only approved ones are written, a rejected one is dropped, a reworded one is written as reworded. Each seeded scenario is a `run.py` with a `- feature: <name>` line in its SCENARIO.md. The line is read outside fenced blocks and HTML comments (a comment opens only where `<!--` starts a line), whole; two feature lines, a top-level `-` field keyed `feature` in another form (`- Feature:`, `- **feature**:`), a fence or comment left open above one, or a SCENARIO.md that cannot be read are a named FAIL in `run` and `ERROR` in `seeded`, never a silent pick or a crash. Gherkin's `Feature:`, nested bullets and `*`/`+` bullets are text: a scenario with no marker reads as before. `scenarios.py seeded <id>` runs it and its children on the files as they are: `SEEDED ✓ <id>` when it fails, with the reason and the last line it wrote (stderr, else stdout), its transcript kept as `run` keeps one (exit 0); `CHECKS NOTHING YET <id>` when it already passes (exit 1: not seeded until it fails); `N/A` (env, exit 4); `ERROR` for a missing, empty or bad feature line, two run files, or a write into the repo, naming what changed (exit 2); it writes no results.json, and finds a write from git status and HEAD, not a tree hash per scenario. An unfiltered `run`, and `check` for a full run on the files as they are, end with `N of M features working` (N: features, a name counted once whatever its case and spacing, whose scenarios all PASS; none in a run that modified the repo; no line when none is marked; after `check`'s verdict line, which the Stop gate reads first; `check` hashes the tree only when its answer needs it). The finish report copies that line as printed, never counted by hand; a seeding task (scenarios written, no feature built) is done with each one `SEEDED ✓` and none of the newly seeded features working (`0 of M` in a new app). Evals: `taste-seed-stories`, `taste-seed-reword`.

- **Adapter files** (`scripts/mech-review.py r2 --adapter <file>`, #16): a TOML file describes a stack to R2 as data: file extensions, test calls and their skip/only markers, function shapes, assert shapes (chains such as `expect(a).toBe(b)`, calls such as `assertEquals(a, b)`), lint suppressions and their reasons, mutation skip markers and config files, and a lexer table (comments, strings, regex literals, brackets). ekit's own scanner reads the source with it; the file holds no regex. `--stack` names the file's stack. A bad file is a usage error that names the field; a source file that does not balance under it is an R2 `needs-human` fail. TS ships as `scripts/mech_review/adapters/ts.toml`, with the same R2 entries as the built-in. Needs python 3.11+ (`tomllib`) only when `--adapter` is given; R2 only for now; the built-in stacks are unchanged. Format: `docs/mech-review-ci.md#adapter-file`.

- **R1 and R4 through an adapter file** (`scripts/mech-review.py red --adapter <file>`, also `all`, #18): the file's `[run]` table says how one test runs by name (words after the test command with `{path}` and `{name}`, how a name part is quoted, the runners of the stack and which one a checkout uses, paths linked into the worktree) and how a run reads (exit code plus `passed`, `failed`, `skipped`, `build`, `no_test` and `env` patterns, compiled at load; one that matches empty text, a command with unbalanced quotes, or a runner command no `when` picks is a load error). `pass` needs a counted passed test; a test that did not run reads `none`. A new test that does not build on the base is compile-red, as with the built-ins. `[commands]` names the stack's install, build, lint and test commands (each required, `""` for none; a missing one is a load error that names it, and a declared-none install or build is named in `red`'s and `all`'s `notes`); R1 and R4 use test only, and a missing runner's `n/a (env)` note names the install command as the fix. A file without `[run]` stays R2 only for R1 and R4 (R3 through a file: #19). The workflow passes no adapter file yet; `tests/mech-review-workflow.test.sh` holds the rule that an adapter's commands run only in the jobs that run PR code and reach `run:` steps only through `env`. Format: `docs/mech-review-ci.md#run-side-r1-and-r4`.

- **Stack plan and the drift check** (#56): `.ekit/stack-plan.toml` lists a repo's stacks (`[[stack]]`: name, folder, adapter: a built-in or an adapter file path, status `planned` | `current` | `retiring`, optional `target-os`) and an `ignore` list of folders. `mech-review.py drift --base B --head H` compares it with the tracked manifests, git only: a manifest no stack covers (outside fixture, vendor and build folders and `ignore`) gives one `fail` entry per PR, check `D`, new class `adapter-fix`, naming every such manifest, waivable with `/mech-waive D-<id>`. The base branch's plan judges; a PR that edits the plan or an adapter file and adds no manifest is judged by its own; a manifest is any name the built-ins or either plan's adapter files list (a base plan that does not read too, entry by entry). A planned entry may name an adapter file not written yet by its path (a `/` or `.toml`; any other value must be a built-in): not proven, it covers nothing. - **R3 shard count (python)** (#64): the `baseline` step runs the whole suite once at head and takes the session time from pytest's JUnit XML (`--junit-xml`, so a repo's `-q` or colour does not hide it) as the measured test time (`checks.R3.timing.baseline_test_s`), and mutmut's listing step counts the mutants on changed lines (`mutants`); none on a changed line runs no shard, as for rust. The suite and the listing each get `mutation-budget`. The count is then `min(4, mutants, ceil(estimated minutes / (budget / 2)))`, as for rust: the estimate is the mutants under `max-mutants` times the suite's test time, so a small python PR gets one shard. A baseline that measured nothing (no mutmut, a red suite or one with no session time in its JUnit XML, a listing that did not end) keeps one shard per changed file, at most 4, and its note says why (`test time not measured (...)`). The workflow's `baseline` job sets up the python venv for this (pytest and mutmut, as the mutants job does), and runs `extra-apt-packages` and `setup-command` for python as for rust. ts keeps one shard per changed file.
- **R3 cap and risk order (ts)** (#63): a big TypeScript PR stays within `max-mutants`, as rust and python do. Stryker selects no mutant by name, so the cap picks changed lines: Stryker's own instrumenter (`@stryker-mutator/instrumenter`, run under `node` from the Stryker install) lists the mutants before the run, each mutant's risk class comes from its mutator in #26's order (branch conditions, then returns and boolean literals, then arithmetic, then the rest, strings last), and mutants go riskiest first (ties by file and line), each bringing every line it spans, while the mutants those lines make stay within `max-mutants`; only those lines go to `--mutate`, and every run picks the same lines. The listing is made twice in one `node` call: with the repo config's `mutator.excludedMutations` off (the config read as data, when it is JSON), for the under-cap decision, the pick and `total`, and with every mutator excluded, an upper bound that guards the run; an `Ignored` mutant counts in neither `tested` nor `total`, so a PR whose run fits under the cap is not capped by mutants its config excludes. A Stryker config that is code (`.js`, `.mjs`, `.cjs`) is never run to read it: the cap is then not applied, every changed line runs, and the note says why (as for a JSON config that is malformed or sets `ignorers` or `ignoreStatic`). The count past the cap is then the run's own, the same in the note and the partial entry. Type-only code makes no mutant and never takes the cap. The rest are untested: R3 reads `partial (tested/total)`, never `pass`. A run that makes more than the upper bound on its picked lines is `n/a (env)`; with no listing (no `node`, `npx stryker`, a pnpm or Yarn PnP install, a malformed row, one of the two lists missing) the cap is not applied and the note says why, naming the row or the list. A run the budget stops is `partial`, never `pass`, and a mutant it never reached (`Pending`) is untested, not MISSED. Under the cap every changed line runs, as before.
- **The layering test finds the engine's modules from its package directory** (#82): `tests/mech-modules.test.sh` imports every `scripts/mech_review/*.py` alone, so a new module is checked with no edit to the test (the hand-kept list had already missed `globs`, `stack` and `waiver`); AGENTS.md drops the rule about adding a module to the list.

### Fixed

- **merge counts only its own stack's mutants results** (#62): every `mutants` result names the stack and project dir it ran for (`stack: {stack, project_dir}`, beside `shard`), and `merge --stack S` (with `--project-dir D`, new, when given: the folder too) counts only the results that name this leg. A result for another stack or folder, one with no stack field, or a malformed one (an empty name too), is one CI `fail` entry naming it and its shard (`mutants shard 1/2 produced no result: result is for stack rust in ., not python`), never counted; #42's shard checks apply to the leg's own results. In `mech-comment.py --stacks`, a stack given twice (by name, or by stack and project dir) is no longer the crash comment: it counts once (the first row), with one CI `fail` entry naming it however many repeats (`stack api (python in api) given twice; the second is not counted`) in the sticky comment, also when the first row has no result, failing the check, while the other stacks still report. The workflow's merge calls pass `--project-dir` once the owner edits them; until then the stack alone is compared.

- **python: R2 was blind to tests of a class whose TestCase base comes from another module** (found by #21's census: `class RepoAdapterRunSide(Fixture)` with `from test_adapter_run import Fixture`, 9 tests on ekit's own suite): the python scanner now counts a class with `test*` methods as a test class when one of its bases is a name that is not `object` and not a non-test class of the same file (an imported base, `base.Shared` too); a mixin with `test*` methods on such a base is guarded as well. A class with `test*` methods and no base, or only `object`, stays a non-test unless it is named `Test*`, as pytest treats it. Statically, in the file alone (no import is followed), and only in a file pytest collects tests from (`test_*.py`, `*_test.py`): in `conftest.py` or a helper module a fake's `test_connection` on a foreign base is no test (renaming it is no R2 entry, and it does not count in assert density). The explicit cases (`Test*` names, `TestCase` bases) hold in every file. A class reached through a same-file helper base counts too (`class _Base(Case)` with no tests, then `class Real(_Base)` with tests, at any depth): the helper passes its imported root on to its subclasses without counting itself (found by R0's census on #76: 6 tests R2 did not guard).

- **ts: R1 and R4 found no test inside a `describe` under real vitest** (#21's runtime half found it): the one-test pattern joined describe and test names with ` > ` (`-t '^Calc > adds$'`), but vitest (2.1.9 and 3.2.7) matches `-t` against the names joined with a space, as jest (29.7.0) does, so the run selected nothing: R1 read `none` (cannot be proven red) and R4 `did not run at head` for every such test. The built-in ts adapter and `ts.toml`'s vitest runner (`separator = " "`) now join with a space; regex characters stay escaped, so the pattern still selects that one test. Test names in entries keep ` > `.

- **`mech-review.py resolve` from a subdir** (#29): with `--repo` (or the current dir) inside a repo's subdir, auto read the tree relative to that subdir and printed a wrong `project_dir`; it now reads the tree from the repo root. `resolve --help` lists the options only, with no text of its own: the main `--help` describes `resolve`.
- **Stop gate: a blocked report no longer makes a later done true** (predates this release): a `done` report on a tree that only a `blocked` report was given for runs the verify commands again; before, it was let through unchecked.
- **Scenario runner**: a background child (`server &`) is stopped with its scenario on POSIX too (its process group), as on Windows (its job); `--repo` naming no directory says so (exit 2), not "no scenarios found".
- **R3's runner over budget on an OS without process groups** (#34): no `os.killpg` or `SIGKILL` (Windows) stops the run with `SIGTERM` instead of raising. `MECH_TEST_STUB` may be a `.py` file, run with the engine's Python (Windows starts no script by its shebang).
- **Python 3.9 and 3.10** (no `tomllib`): R2's mutation-config rule for python compares the text of pyproject's `[tool.mutmut]` table, so a version bump beside it is no mutation-config change there either (it was one); the TOML tests assert the text R3 writes on every version.
- **doctor on Windows** (#46): entries name paths with `/` (`docs/usage.md`), and a copy error worded `[WinError N] ...` gives its message without the temp path.
- **ekit's own suites on Windows** (#46): the Python tests pass natively (`py -3 -m unittest discover -s tests/py`): temp files Windows can reopen, Git Bash in place of a bare `bash`, link text and file names Windows cannot hold through the index, a watchdog without `SIGALRM`, the git dir made read-only by ACL. A case that needs named pipes, or mutmut's POSIX copy errors, skips with that reason on Windows.

- **`merge` checks which shard each result is** (#42): a shard given twice, a shard index missing for `--shards`, or shards that disagree on head, base or cap give one CI `fail` entry; before, a duplicate shard was counted twice. `mutants` results now carry `shard: {k, n, max_mutants}`; a malformed or dropped field is named, and `--envelope K` given twice is a usage error. The mutants job's CI entries now reach the sticky comment and fail the check (before, `report` kept only R3's entries from it). A check with status `fail` now fails the summary and the check even with no fail entry.
- **R3 (python)**: a mutant the budget never reached, including one still waiting for its whole-suite retry, read MISSED, so a PR with real tests could read as many failures. It is now untested: R3 is `partial`, with no MISSED entry. A mutant that ran and survived its retry is still MISSED.
- **`--mutation-budget nan` / `inf`**: crashed `baseline` with a traceback; now a usage error (exit 2).
- **Scenario runner and Python bytecode** (#43): `__pycache__/` and `*.pyc` no longer count as a scenario writing into the repo, and scenarios run with `PYTHONDONTWRITEBYTECODE=1`, so `mech-review-python/real-mutmut/untracked` passes on a plain run.
- **Scenario runner keeps a failed transcript** (#44): a failure is copied to `<git dir>/ekit/failed/<id>.log` (results.json: `failed_transcript`) and stays there until the same scenario fails again, whatever runs in between.
- **ekit's own suites** (#46 items 1–3): `.gitattributes` checks every file out with LF; `tests/lib.sh` has a python `sha1` helper in place of `sha1sum`; a symlink test skips with the reason when the OS refuses links.
- **ekit's own Python suite is green as root** (#80): the two read-only git dir tests of task verification and doctor's unreadable-directory test injected their refusal with a mode change, which root ignores; they now get the OS's `PermissionError` at the point where ekit writes (task-verify's `open`) or reads (the copy's `os.scandir`), so they prove the same reaction for any user. No production behaviour changes.

## 0.5.0

### Added

- **`stack: auto`** (`mech-review.yml`, `scripts/mech-review.py resolve`): the reusable workflow's `stack` input defaults to `auto`. A new `stack` job, git only, finds the one project from the tracked manifests with doctor's detection, at the PR base and head, and every later job (each toolchain `if:` included) reads the stack from its outputs through `env` or `if:`. `project-dir` left at `.` takes the dir found; a dir the caller set is never replaced. It runs only for comments from `OWNER`, `MEMBER` or `COLLABORATOR`, never for a bot or the sticky comment, and never runs PR code. ci-doctor writes the caller.
- **Ready-made waiver lines**: the sticky comment shows, under each `fail` entry, the line to post (`/mech-waive <id> <why this is OK>`), plus one block for all fail entries when there are several.

- **`stack` default**: was `rust`. A caller that leaves `stack` out now gets the stack its repo has; a repo with several projects (or none) and no `stack` input now fails with a message instead of running as rust. Set `stack` (and `project-dir`) to keep the old behaviour.
- **Waivers**: a reason still reading `<why this is OK>` (or any reason wholly in `<…>`) does not waive, and a comment edited after posting does not waive: anyone with write access can edit another person's comment while the author shown stays the same. The sticky comment names each ignored waiver and why; post a new comment instead.

### Fixed

- **R3 (python)**: a repo whose tests read tracked files outside the sources and `tests/` (`docs/`, `config/`, `scripts/`, `README.md`) failed R3 with `baseline tests fail at head: mutants not run`, because mutmut 3.8.1 copies only the sources, `tests/` and a few root files into its `mutants/` sandbox (#7). Source entries, `mutants/`, untracked files and mutmut's own defaults are never listed, nor is an entry holding a symlink mutmut cannot copy. Root test config (`pytest.ini`, `tox.ini`, `conftest.py`) now applies in R3 as in R1. `source_paths` and `only_mutate` stay valid TOML for names outside the BMP.
- **doctor (python)**: the trial runs the suite once more inside a copy built the way R3's mutmut sandbox is. A dangling or looping link under `tests/`, which stops or hangs mutmut's copy, is named without copying. The trial gains `sandbox: pass|fail|skipped`. ## 0.4.0

### Added

- **Scenario artifacts**: each scenario gets `EKIT_ARTIFACT_DIR`. Files it saves there, screenshots first, are kept beside its transcript in `<git dir>/ekit/<tree>/<id>/` and listed under `artifacts` in results.json; a scenario that saves nothing leaves no dir. taste-it's Web UI driver saves a screenshot of each asserted state, and the finish report cites the paths: in a scenario row, and in the Needs-you block of a 👤 visual check. The assertion stays on text: a screenshot is the reviewer's proof, never the pass. The hooks only read those records: the commands run under the session's permission rules and sandbox, never from a hook. A sandbox that keeps the git dir read-only gets exit 3 and the same call outside the sandbox as next step.
- **Task hook** (`TaskCreated`, `TaskCompleted`), for sessions that have a task list: a task whose description carries a ``Verify: `<command>` `` line cannot be marked completed until that command passed on the files as they are now. The command is kept from the first time the task is seen. A pass in a linked worktree counts from the main checkout while that worktree's files are unchanged. Tasks without the line are not gated. In agent teams, where a teammate's turn end fires the hook, the block is given once per set of file contents.

- **taste-it**: a bug from use (a user's report, one met while using the deliverable, or one handed over by failure-triage) becomes a scenario before any fix. A `FAIL` on the unfixed code is the proof that the bug is real; a `PASS` means not reproduced: no code changes, and the scenario is not kept. failure-triage hands a real bug over when a user would hit the symptom and no scenario covers it: the symptom only, never the cause. New eval case `taste-act-bug-report`.

### Changed

- **finish**: the report's `Env:` line is the output of `preflight.sh --env`, a probe of what the shell can do (write outside the project, bind a port). Reports said "sandboxed" in sessions that had no sandbox: the skill asked for the word and gave no way to know.
- **finish**: which report to give is decided by what is left. Work the agent can still do comes first; everything done with only the user's part left is `done except`; `blocked` is for work that cannot go on. With every command green and one item needing the owner, one run reported `blocked` and its twin `done except`.
- **Finish gate**: `## Finish: done` now needs every verify command of the session green on the current files (`task-verify.py check`). A unit's pass from before a later edit does not count, and an orchestrate session with no verify command cannot report done: the block gives the `declare` call. `## Finish: blocked` is unchanged, and no other stop is checked.
- **Finish gate**: a `## Finish: done` report repeated right after a block is checked again. The gate used to let every stop after a block through (Claude Code's `stop_hook_active`), so an agent that answered a block with the same report, having run nothing, got past red scenarios and red verify commands alike. A stop without a `done` report is still let through after a block.
